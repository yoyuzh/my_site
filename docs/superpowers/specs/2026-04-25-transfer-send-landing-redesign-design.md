# `/dashboard/transfer-send` 分享式发送页改版设计

## 目标

- 仅改造 `frontend/src/pages/TransferSend.tsx` 对应的 `/dashboard/transfer-send` 页面。
- 将当前偏技术说明的发送页改为更像“分享落地页”的体验，让用户先理解“怎么把文件交给对方”，再理解具体方式。
- 保留 `发送 / 接收` 顶部切换，但在发送页内部把 `在线 P2P` 与 `离线快传` 设计成平级方案，通过按钮切换，不刻意放大技术差异。
- 使用更偏用户的语言，弱化 `WebRTC`、`DataChannel`、`信令` 等实现术语。
- 强化创建成功后的结果展示，优先突出取件码、接收入口、复制动作、过期时间和当前状态。
- 保留必要失败反馈，让用户在取件失败、会话过期、对方未进入、连接失败时知道下一步该做什么。

## 非目标

- 不改造 `frontend/src/pages/TransferReceive.tsx` 的独立接收页结构。
- 不改动后端接口、传输协议、会话规则、P2P 建链逻辑或离线快传逻辑。
- 不扩展到 `/dashboard` 下其他页面。
- 不把这次改版做成“技术控制台”或“网络诊断页”。

## 用户体验方向

本次采用已确认的 `B. 分享落地页型` 方案。

页面气质应更接近“我准备把文件分享给别人”，而不是“我正在配置一种传输协议”。用户在进入页面后，应该先看到：

1. 这是一个把文件发给对方的页面。
2. 我可以选一种发送方式。
3. 创建后，对方怎么来拿文件会非常清楚。

界面语言尽量使用下面这类表达：

- `在线发送`
- `稍后接收`
- `把链接发给对方`
- `把取件码告诉对方`
- `对方进入后会自动开始`

尽量少直接展示下面这类技术表达，除非只在次级说明中简短出现：

- `WebRTC`
- `P2P`
- `信令`
- `直连协商`
- `候选地址`

## 页面结构

### 1. 顶部页头

- 保留当前 `发送 / 接收` 顶部切换。
- `发送` 为默认主视图。
- 标题和说明改成用户导向，例如：
  - 标题：`发送文件`
  - 说明：`创建一个取件入口，让对方在线接收，或稍后再来取走。`

### 2. 发送方式切换

- 在发送主卡片顶部放置两个平级按钮，用于切换：
  - `在线发送`
  - `稍后接收`
- 两个按钮视觉权重一致，不出现“高级模式 / 普通模式”这类暗示。
- 每个按钮只给一行简短解释：
  - `在线发送`：`对方现在就能进入接收页，连接成功后直接开始。`
  - `稍后接收`：`先生成取件码，对方稍后凭取件码来取。`

### 3. 主操作区

- 无论选择哪种方式，主操作区结构尽量一致：
  - 当前方式说明
  - 选择文件按钮
  - 一句补充提示
- 按钮文案统一为用户语言，例如：
  - `选择文件并创建`
- 在未创建前，页面重心是“开始发送”，而不是技术背景介绍。

### 4. 结果卡片

- 成功创建后，在主区域原位切换为结果卡片，不要让用户到右侧或下方再找关键信息。
- 结果卡片必须优先显示：
  - 取件码
  - 复制取件码按钮
  - 接收链接（仅在线发送展示）
  - 复制链接按钮
  - 过期时间
  - 当前状态
- 在线发送状态下，状态文案要围绕“对方是否进入”“是否开始传送”“是否已完成”来组织。
- 稍后接收状态下，重点展示本次文件列表、取件码和过期时间。

### 5. 辅助信息区

- 页面可以保留次要辅助区域，但权重必须明显低于主操作区和结果卡片。
- 适合放：
  - 如何接收的一句话提示
  - 最近创建的稍后接收记录
- 不再把辅助区做成与主操作区竞争注意力的第二主栏位。

## 两种发送方式的统一表达

虽然在线发送与稍后接收的技术原理不同，但界面层应尽量统一心智模型：

- 两者都属于“把文件交给对方”
- 两者都通过“创建一次发送入口”开始
- 两者都在成功后给出“告诉对方怎么拿”的结果

界面差异只体现在结果与状态上：

- `在线发送`
  - 展示接收链接
  - 展示等待对方进入、建立连接、发送进度、完成状态
- `稍后接收`
  - 不展示接收链接
  - 展示文件清单与过期时间
  - 更强调“对方稍后可凭取件码接收”

## 状态与失败反馈

状态与失败提示必须清楚、短句、能指导下一步，不用协议术语吓用户。

### 在线发送常见状态

- `正在准备发送入口...`
- `发送入口已创建，把取件码或链接发给对方`
- `正在等待对方进入`
- `对方已进入，正在建立连接`
- `正在发送`
- `发送完成`

### 失败提示原则

- 先说用户现在遇到了什么。
- 再给出下一步建议。
- 不直接暴露底层错误细节，除非需要调试。

### 建议文案

- 取件码无效：
  - `这个取件码不可用了，请重新创建一次`
- 会话过期：
  - `发送入口已过期，请重新创建一次`
- 对方未进入：
  - `对方还没进入接收页，你可以先把取件码或链接发给对方`
- 连接失败：
  - `这次连接没有建立成功，可以重试一次`
- 当前网络下无法完成在线发送：
  - `当前网络下在线发送失败，建议改用稍后接收`

## 文案策略

- 页面主文案统一面向普通用户，不假设用户理解传输协议。
- 技术细节最多作为次级说明存在，不占主标题、主按钮、主状态位。
- 所有 CTA 文案都要表达动作结果，而不是实现手段。

推荐：

- `选择文件并创建`
- `复制取件码`
- `复制接收链接`
- `继续发送`
- `换一种方式`

避免：

- `启动 P2P 会话`
- `开始信令协商`
- `创建 DataChannel`
- `重新发起握手`

## 实现边界

- 本轮只做前端页面改版，保持现有接口和交互能力可用。
- 业务逻辑尽量复用现有 `frontend/src/pages/TransferSend.tsx`、`frontend/src/lib/transfer.ts`、`frontend/src/lib/p2p-transfer.ts`。
- 如需前端实现，本次由本机 Gemini 负责 UI 改造部分，但提示词必须严格限定：
  - 只改 `/dashboard/transfer-send`
  - 不改后端
  - 不擅自重构其他页面
  - 不新增未确认的业务流程

## 验证标准

- 用户进入 `/dashboard/transfer-send` 后，可以在几秒内理解“我该怎么把文件发给别人”。
- 在线发送与稍后接收可以通过同一层级按钮切换。
- 创建成功后，取件码与复制动作是最显眼的信息。
- 在线发送失败时，能看到明确提示和可执行建议。
- 页面整体观感更接近分享页，而不是技术调试页。
